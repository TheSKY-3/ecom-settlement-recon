# 设计文档：电商多平台结算对账 Agent（ecom-settlement-recon）

> 日期：2026-09-26。状态：已获口头批准（对话记录），本文件是"讲明白版"成文。
> 读完你应该能回答：这项目给谁看、做什么、怎么证明它有用、每一步为什么存在。

## 0. 一分钟版

给"多平台开店的电商卖家"做的**自动对账工具**：把三本账——买家支付流水、订单账本、平台账单——互相核对，自动找出对不上的地方（差异），并说明每处差异属于哪类错、证据是什么。确定性的规则引擎干所有主活，AI 模型只出现在两个受控出口：解释疑难差异、回答自然语言查账问题。因为是"自己埋雷、自己判卷"，所有指标（检出率、误报率、归因准确率）都有标准答案可算。

## 1. 目标与非目标

**目标**
1. 确定性管道：无 AI 模型参与，跑通三本账全量核对，产出差异清单 + 审计链 + 报告。
2. 受约束 Agent 壳：两个出口（`attribute(差异)` 带证据归因、`ask(问题)` 带引用查账），五件套护栏。
3. 可信评测：六类人为差异 + 自然差异，检出率/误报率/归因准确率成表；第二数据集（BenchRec，银行流水对账）跨域重跑匹配引擎。
4. 项目定位：通用对账 Agent → 合成数据量化评测。

**非目标**
- ~~不做网页界面（时间盒内可选项）~~（2026-09-26 用户拍板加本地工作台，另见 [workbench-design.md](2026-09-26-workbench-design.md)）。
- 不做发票/报销/报税等泛财务。
- 不声称真实业务上线效果——对外一律说"本地原型 + 合成数据评测"。

## 2. 总体架构（两层）

```
┌─ 确定性管道（无 AI 模型，可复现可重跑）──────────────────┐
│ ingest → normalize → match → classify → audit → report   │
└───────────────┬───────────────────────────┘
                │ ①低置信度差异 ②自然语言问题
┌───────────────▼───────────────────────────┐
│ 受约束 Agent 壳（自研循环 + DeepSeek）       │
│ attribute(diff)  /  ask(question)          │
└──────────────────────────────────────────┘
```

**分工原则**：步骤能提前画成流程图的用代码写死；只有"下一步取决于看上一步结果的理解"的活才交给 AI。让模型碰主匹配路径是反模式（不可复现、不可审计、贵、慢）。

## 3. 组件与数据流

```
data/raw/*.csv ──build──▶ data/olist.db（干净底座）
                              │
              src/synth/ ─────┼──▶ data/synthetic/clean/  干净三本账（含新生成的平台账单、退款流水）
              （造账+埋雷）    └──▶ data/synthetic/dirty/   埋雷后的三本账 + ground_truth.csv
                                            │
                              src/engine/ ──▶ 差异清单 + 审计链 + 报告（docs/reports/）
                                            │
                              evals/ ──────▶ 对照 ground_truth 判分 → 评测表
```

| 组件 | 职责 | 关键决定 |
|---|---|---|
| `src/synth/rules.py` | 规则卡：平台账单怎么算、退款什么时候该有 | 佣金统一 20%（可配置），规则卡可调 |
| `src/synth/bills.py` | 生成干净的平台账单 | 只给"未取消"订单开账单；应付卖家 = 货款 + 运费 − 佣金 |
| `src/synth/refunds.py` | 生成干净的退款流水 | 取消/不可达且已付款的订单，全额退款 |
| `src/synth/injectors.py` | 六类埋雷器（单边账/金额不符/状态不一致/退款遗漏/重复结算/版本差异） | 每单最多中一种雷，与自然差异错开 |
| `src/synth/ground_truth.py` | 标准答案读写 | `gt_id, order_id, diff_type, target_side, description` |
| `src/engine/matcher.py` | 三本账互对 | 订单号为主键 + 金额容差 ±0.005 |
| `src/engine/classifier.py` | 差异分六类，规则树，输出置信度 | 低置信度 → 升级 Agent |
| `src/engine/audit.py` | 审计链 | 每步记录带文件指纹，串联成链 |
| `src/agent/loop.py` | 五件套护栏的自研循环 | 白名单/预算/留痕/查引用/失败降级 |
| `src/agent/tools.py` | 5 个只读查询工具 | 参数化 SQL，防注入 |
| `evals/runner.py` | 判分出表 | 同一套题可重复跑 |

## 4. 六类差异怎么埋（摘要）

| 类型 | 干净世界的破绽 | 举例 |
|---|---|---|
| 单边账 | 账本有、流水无（或反过来） | 删掉一条支付记录；造一笔没有订单的账单 |
| 金额不符 | 金额算错 | 佣金用了 10% 而不是 20%；漏加运费 |
| 状态不一致 | 取消的订单还在账单里 | 已取消订单被平台照常收费 |
| 退款遗漏 | 该退的钱没退 | 取消单已付款，但退款表里查无此单 |
| 重复结算 | 同一笔账出现两次 | 同一订单两张相同账单 |
| 版本差异 | 新旧两版账单并存 | v1 金额错、v2 正确，引擎须按新版对 |

**隔离规则**：埋雷只落在"干净"订单池上，且避开 P0 盘点出的自然差异订单——保证评测时每颗雷都有唯一归因。

## 5. 错误处理与失败关闭

- 管道任何一步数据不合法（缺列、金额为空）→ 报错退出，不静默跳过（原始层加载同理，重复行不丢、只报告）。
- 引擎结论落报告前必须过验证器：证据逐字段核对；不过 → 结论标"未验证"。
- Agent 任何失败（超预算、引用对不上、工具报错）→ 输出"无法确定 + 已排除项"，绝不编答案。

## 6. 测试策略

- 造数模块：固定随机种子 → 同种子必出同数据（可复现）；每类注入器断言"雷的数量、位置、形状"与标准答案一一对应。
- 引擎：用造数模块造小样本（几十单）做单元考卷；全量跑通作为集成考卷。
- Agent：先离线（不调真模型，用录制的工具返回序列）考五件套行为；真模型只做冒烟。
- 评测：指标计算函数用手工可算的小例子对拍。
